# PRD — LogAI v0.1.5 Closed-Source Release Hardening

**Target:** Codex
**Release:** `v0.1.5`
**Components:** `identity-api`, `logai-api`, `logai-ui`
**Purpose:** Add source-code protection to the same release that implements Schneider EKS container hardening.
**Deployment ownership:** Gamestory owns build/release images and runtime contract. Schneider owns JFrog ingestion, Helm, Argo CD and EKS deployment.

## 1. Objective

Make `v0.1.5` the first deliberately client-distributable, closed-source LogAI release.

For the Python APIs, proprietary Gamestory Python must be compiled with **Nuitka during CI/build** and must not be present as `.py` or `.pyc` in the final distributable OCI images.

For the Next.js UI, ship only the production runtime output required to execute the application. Original TypeScript/TSX source, source maps, tests, Git metadata and development tooling must not be included in the final image.

This work must be combined with the existing Schneider EKS requirements:

- APIs run as numeric UID `10001`;
- UI runs as numeric UID `1000`;
- root filesystem supports read-only operation;
- APIs use `/tmp` for legitimate temporary writes;
- UI runtime config uses `/app/runtime-config`;
- `.next/cache` is writable only if runtime testing proves it is required;
- published images are tagged `v0.1.5`.

## 2. Core Security Principle

Source code is a **build-time asset**, not a client runtime asset.

Target flow:

```text
GitHub source
      |
      v
CI / build environment
      |
      +---- tests
      |
      +---- Nuitka compile (Python APIs)
      |
      +---- Next.js production build (UI)
      |
      v
runtime-only OCI images
      |
      +---- source-leak verification
      +---- runtime/security tests
      +---- vulnerability scan / SBOM
      |
      v
Docker Hub v0.1.5
      |
      v
Schneider ingestion -> JFrog -> Schneider Helm -> Argo CD -> EKS
```

No compilation or obfuscation occurs in Schneider EKS. Nuitka is a CI/build concern only.

## 3. Inspect Before Implementation

Codex must first inspect the existing repositories and CI/release pipeline.

Determine:

- current Dockerfiles and multi-stage build structure;
- current GitHub Actions/release workflows;
- Python entrypoints and packaging;
- FastAPI/Uvicorn/Gunicorn startup mechanism;
- dynamic imports and `importlib` usage;
- Pydantic/FastAPI reflection requirements;
- package data, templates and static resources;
- plugin/module discovery;
- multiprocessing/subprocess behaviour;
- current dependency installation;
- current Trivy/SBOM/signing/attestation steps;
- UI Next.js build mode;
- current source-map settings;
- current contents of final images;
- current Docker Hub publishing mechanism.

Preserve working CI capabilities. Extend the existing release pipeline rather than replacing it unnecessarily.

## 4. Python Release Architecture — Nuitka

Apply Nuitka to:

- `logai-api`
- `identity-api`

Development remains ordinary source-based Python. Nuitka is required only for distributable/release images.

The intended build model is:

```text
BUILDER STAGE
-------------
Python source
Python dependencies
Nuitka
C compiler/toolchain
required headers
tests/build tooling
        |
        | compile
        v
compiled application artifact

RUNTIME STAGE
-------------
compiled application
required runtime libraries
required non-secret resources/config
CA certificates as required

NO proprietary Python source
NO proprietary Python bytecode
NO Nuitka
NO compiler
NO Git metadata
NO tests
NO development tooling
```

Use multi-stage Docker builds unless the existing release architecture provides an equivalent clean separation.

## 5. Nuitka Compatibility

Do not assume that successful compilation means the application is complete.

Codex must inspect and validate anything that relies on Python runtime discovery, including:

- dynamic imports;
- `importlib`;
- FastAPI application discovery;
- Pydantic model loading;
- package resources;
- templates;
- static assets;
- reflection;
- plugins;
- environment-selected modules;
- Uvicorn/Gunicorn integration;
- multiprocessing;
- dynamically loaded dependencies.

Add explicit Nuitka inclusion options only where required by actual application behaviour.

Do not broadly include the entire source tree simply to make compilation succeed.

## 6. Python Runtime Images

The final API images must contain the compiled application artifact and only the runtime dependencies/resources required to execute it.

They must **not contain proprietary Gamestory `.py` or `.pyc` files**.

Third-party runtime packages may contain Python source where technically required. Source-leak validation must distinguish legitimate third-party packages from Gamestory proprietary application code rather than failing blindly on every `.py` file.

The final API images must still satisfy Schneider's runtime contract:

```dockerfile
USER 10001
```

and support:

```text
runAsNonRoot: true
readOnlyRootFilesystem: true
allowPrivilegeEscalation: false
```

Temporary application writes must use `/tmp`.

## 7. Do Not Compile Secrets

No secret may be embedded into the Nuitka binary.

This includes:

- passwords;
- API keys;
- client secrets;
- tokens;
- private certificates/keys;
- Schneider credentials;
- environment-specific secrets.

Secrets remain runtime configuration supplied through the approved deployment mechanism.

Environment-specific URLs/configuration must also remain external where appropriate so the same immutable image can be promoted across environments.

## 8. Binary Hardening

For release builds:

- avoid unnecessary debug information;
- remove/strip symbols where safe and compatible with supportability;
- avoid embedding local developer/build paths where practical;
- do not package generated C/C++ intermediate source into the final image;
- do not package Nuitka build directories into the final image.

Do not apply transformations that make the application unstable merely for marginal obfuscation benefit.

## 9. UI Closed-Source Distribution Standard

The browser necessarily receives JavaScript, so the UI cannot receive equivalent protection to the server-side Nuitka binaries.

For `logai-ui`, produce a production-only Next.js runtime image.

Prefer Next.js standalone output if it is compatible with the current application and existing runtime-config mechanism.

The final UI image should contain only what is required to run, such as:

```text
.next/standalone
.next/static
required public assets
runtime-config mechanism
required Node runtime files
```

It must not contain original Gamestory:

```text
*.ts
*.tsx
source maps (*.map)
source tree
tests
.git
development-only tooling
```

Do not introduce aggressive JavaScript obfuscation in this release unless existing tooling already does so safely. Production bundling/minification is sufficient for `v0.1.5`.

Proprietary algorithms/business rules must remain server-side rather than being moved into browser code.

## 10. UI Runtime Configuration

Preserve the EKS hardening requirement that runtime configuration is generated outside the immutable application tree.

Physical runtime config:

```text
/app/runtime-config/config.json
```

Do not generate it into `/app/public`.

Environment-specific endpoints must be runtime configuration rather than permanently embedded into the Next.js bundle where practical.

The final UI image runs as:

```dockerfile
USER 1000
```

and supports a read-only root filesystem with only the explicitly required writable mounts.

## 11. Final-Image Source Leakage Gate

Add a mandatory CI stage after the final OCI images have been built.

Suggested stage name:

```text
verify-distributable-artifact
```

This stage must inspect the **actual final image**, not merely the build workspace.

Export/extract the image filesystem/layers using an appropriate mechanism such as `docker save` or equivalent.

Fail the release if proprietary Gamestory material is found where it should not exist.

Check for:

- proprietary `.py`;
- proprietary `.pyc`;
- original `.ts`;
- original `.tsx`;
- production source maps;
- `.git` / repository metadata;
- test directories/files;
- build directories;
- Nuitka generated C/C++ intermediates;
- compiler/build tooling accidentally copied into runtime;
- obvious development-only artifacts.

Design checks around known Gamestory application paths/packages to avoid false positives from legitimate third-party runtime dependencies.

## 12. Binary Inspection

Inspect the compiled API artifact with appropriate Linux tooling, for example:

```text
file
strings
readelf
objdump
```

where available and useful.

The purpose is not to prove that reverse engineering is impossible. The purpose is to catch accidental leakage such as:

- original source files;
- large source-code fragments;
- developer filesystem paths;
- debug metadata;
- credentials/secrets;
- generated build-source paths.

Nuitka raises the reverse-engineering barrier; it does not provide cryptographic secrecy.

## 13. Runtime Regression Gate

The compiled applications must behave identically at their public runtime boundary.

For each API validate:

- process starts successfully;
- expected environment configuration works;
- database connectivity works;
- `/health` succeeds;
- representative smoke endpoints succeed;
- graceful shutdown works;
- startup does not depend on source files;
- runtime does not attempt to write beneath `/app`;
- no import/module/resource errors occur.

Run using Schneider-equivalent restrictions:

```bash
docker run \
  --user 10001 \
  --read-only \
  --tmpfs /tmp \
  <image>
```

## 14. UI Runtime Regression Gate

Validate the production-only UI image under Schneider-equivalent constraints:

```bash
docker run \
  --user 1000 \
  --read-only \
  --tmpfs /tmp \
  --tmpfs /app/runtime-config \
  <ui-image>
```

Add a writable `/app/.next/cache` mount only if runtime testing confirms it is necessary.

Validate:

- `/` responds;
- runtime config is generated;
- browser-facing config is accessible;
- API base URLs resolve through runtime configuration;
- no source map is publicly exposed;
- no read-only filesystem errors occur.

## 15. Performance Validation

Nuitka must not be accepted solely on functional correctness.

Compare the current source-based/release baseline against the compiled build for:

- startup time;
- representative API p50/p95/p99 latency;
- memory consumption;
- CPU consumption;
- final image size.

For this first implementation, report material differences rather than inventing arbitrary failure thresholds.

Any substantial regression must be investigated before release.

## 16. Preserve Existing Supply-Chain Controls

Do not remove or weaken existing:

- unit/integration tests;
- Trivy/security scans;
- SBOM generation;
- CycloneDX output where currently used;
- signing/attestation/provenance steps;
- release evidence;
- immutable versioning controls.

The SBOM must describe the final distributable artifact/dependencies as accurately as the existing toolchain allows.

## 17. Versioning

This work is included in the existing EKS hardening release.

Current:

```text
v0.1.4
```

New:

```text
identity-api-v0.1.5
logai-api-v0.1.5
logai-ui-v0.1.5
```

Do not mutate `v0.1.4`.

Do not use `latest` as the deployment contract.

## 18. Build Once, Promote the Same Artifact

The release principle is:

```text
source commit
    |
    v
CI build once
    |
    v
immutable v0.1.5 image + digest
    |
    +--> release validation
    +--> client-local
    +--> Schneider JFrog
    +--> UAT
    +--> production
```

Do not rebuild source separately for Schneider, UAT or Production.

Environment differences belong in runtime configuration/secrets/infrastructure, not in separately compiled application binaries.

## 19. Publish to Docker Hub

After all gates pass, publish:

```text
chrismdgs/gamestory_logai_schneider:identity-api-v0.1.5
chrismdgs/gamestory_logai_schneider:logai-api-v0.1.5
chrismdgs/gamestory_logai_schneider:logai-ui-v0.1.5
```

Use the existing authenticated CI publishing mechanism where available.

Never commit or log Docker Hub credentials.

## 20. Post-Publish Verification

Fresh-pull the published artifacts and repeat critical acceptance checks against the pulled images.

Record:

- component;
- tag;
- immutable image digest;
- Git commit SHA;
- build/CI run;
- SBOM reference;
- security scan result;
- source-leak verification result;
- runtime/security test result.

The artifact validated after pull must be the artifact handed to Schneider.

## 21. Schneider Ownership Boundary

Codex must **not create or modify Schneider's Helm chart** as part of this work.

Gamestory delivers:

- compliant OCI images;
- tags/digests;
- runtime environment contract;
- numeric UID;
- ports;
- health endpoints;
- writable mount requirements;
- database/authentication requirements.

Schneider owns:

```text
Docker Hub artifact ingestion
        |
        v
Schneider JFrog
        |
        v
Schneider Helm chart
        |
        v
Argo CD
        |
        v
Shared EKS
```

## 22. Required Codex Execution Approach

### Phase 1 — Inspect

Inspect repositories, Dockerfiles, CI workflows, application startup, dynamic Python behaviour and UI build configuration.

### Phase 2 — Proposal

Before broad implementation, report:

- proposed Nuitka build strategy;
- required Nuitka options/plugins;
- Dockerfile changes;
- CI changes;
- UI production packaging changes;
- expected final runtime contents;
- identified compatibility risks.

Prefer the smallest robust change.

### Phase 3 — Implement

Implement both API release builds and UI production-only packaging.

### Phase 4 — Validate

Run functional, EKS-security, source-leak, binary-inspection, supply-chain and performance checks.

### Phase 5 — Release

Build and publish `v0.1.5`, fresh-pull it, revalidate it, and produce the Schneider runtime handover.

## 23. Definition of Done

`v0.1.5` is complete when:

- `identity-api` proprietary Python is compiled by Nuitka;
- `logai-api` proprietary Python is compiled by Nuitka;
- final API images contain no proprietary Gamestory `.py`/`.pyc`;
- APIs run as UID 10001;
- APIs work with read-only root filesystem and `/tmp`;
- UI is a production-only Next.js runtime image;
- final UI image contains no original `.ts`/`.tsx` or production source maps;
- UI runs as UID 1000;
- UI works with read-only root filesystem and dedicated runtime-config storage;
- final images pass source-leak inspection;
- compiled binaries pass leakage/debug inspection;
- existing security scans/SBOM/release controls remain operational;
- runtime regression tests pass;
- performance comparison is recorded;
- exact published images are fresh-pulled and revalidated;
- immutable tags/digests and Git SHA are recorded;
- Schneider receives the runtime contract required to build its Helm chart.

The security objective is not to claim that reverse engineering is impossible. The objective is that **Gamestory source code never forms part of the client-distributable runtime artifact**, and recovering proprietary server-side implementation requires materially harder native-binary reverse engineering rather than extracting readable Python source from an OCI image.
